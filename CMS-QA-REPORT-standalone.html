Scope and ground rules observed

  • Payments were not tested, at your instruction. No notification was ever sent — the Articles form has a "Send Notification" checkbox, and no record was ever saved with it enabled.
  • Only records I created myself were edited or deleted. Your existing staging content was left untouched. Every test record has been removed.
  • Two findings are marked "needs check" — an intermittent login failure and a hero field behaviour I saw once. Everything else was reproduced or read directly from the API.
  • Rendering ran on software WebGL, so timings are worst-case. All findings below are about behaviour, not speed.

Verified working

Tested and correct — recorded so it isn't re-tested.

Hero Section — full cycle passes

  • Create → 201, item appears in the CMS list and in the public API within seconds.
  • Edit → 200 /hero-section/5, new title reflected immediately.
  • Delete → confirmation dialog naming the item, 200, removed from both the CMS list and the public API.
  • Frontend propagation → the new slide and its CTA rendered on the staging website without a redeploy.

Other things that work

  • Form validation is genuinely good — empty submits are blocked per-field ("Title is required", "Published Date is required") and no network write is attempted.
  • Auth API is solid: no user enumeration (unknown user and wrong password return an identical 401), and no lockout under repeated attempts.
  • Staging banners are clearly marked on both the CMS and the website.
  • Draft / Published / Archived tabs and the "items awaiting review" dashboard counter are wired up correctly.
  • Media picker selection, ordering controls and delete confirmations all behave sensibly.

Not covered

Excluded by instruction

  • Payments, orders and donation checkout.
  • Notification sending (the config issue is reported as finding 9).
  • Editing or deleting your pre-existing staging content.

Blocked or not reached

  • Create/edit/delete on the 19 content collections could not be completed — finding 2 blocks it at the form level, and finding 1 blocks adding any new image.
  • Roles and permissions editing, forms builder submissions, and dashboard drag-to-reorder persistence.
  • Mobile/tablet layout of the admin panel.

Suggested order of work

  1. 1 and 2 — the two blockers. Until media upload works and the Publications picker opens, an editor cannot publish a single article. Everything else is secondary.
  2. 3 — the two collections returning 500 on every dashboard load.
  3. 4 — the hero Internal Route default, which can silently point the homepage at a dead end.
  4. 5, 6 — the user list showing hashes and the collections showing "0 fields": both make admin screens unusable.
  5. 7, 9 — environment bleed: staging writing production asset URLs, and staging pointing at production payments and notifications.
  6. 10–22 — validation, labelling and copy fixes.
